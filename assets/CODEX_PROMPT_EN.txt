1. PRODUCT PURPOSE

Create a Sydney CBD simulator for selecting cooling-fog installation locations and comparing their estimated local air-temperature reduction. The user evaluates pedestrian demand, street-level air temperature, when natural shade arrives, and how quickly a location cools naturally. They select a candidate, install or remove a fog unit, adjust output, and compare the same location before and after installation over the day.

This is a cooling-fog placement simulator. Do not build a shaded walking-route planner, directions interface, or route-oriented sidebar.

7. COOLING SIMULATION AND UI STATE

The left inspector shows ranked candidate locations, priority score, pedestrian flow, local air temperature, shade arrival, predicted natural temperature change in one hour, installation status, fog output and before/after temperatures. The selected candidate and map marker must agree.

Provide install/remove controls and a recommendation button that selects the current highest-ranked candidate. Keep installed units when the user changes selection. If output is shared across all installed units, label that scope clearly. An output of zero must produce no cooling or fog emission.

Use an 08:00-18:00 timeline with play/pause. Changing time updates sunlight, actual scene shadows, shade timing, sample temperatures, pedestrian flow and ranking. Include weather scenarios and toggles for temperature, pedestrians, trees and shadows. Explain the distinction between a visual shadow toggle and a tree-presence change that affects shade calculations.

Before/after comparison must use the same time, weather and colour scale. Show hotter streets more clearly in orange and red, with cooler areas in teal. Use the demo's shared 27-36 degrees Celsius scale and label it. Render heat along actual streets and pedestrian surfaces, not as a red tint over the entire city. Keep street air temperature distinct from land-surface temperature.

Installed units create soft animated mist and a local cooling footprint. Cooling should weaken with distance, higher humidity and stronger wind, and increase with output within bounded assumptions. Units that are removed, disabled or outside their influence radius must not cool a location. Do not add overlapping effects without a justified model; the demo takes the largest local reduction.

Keep thermal calculations separate from rendering. Reuse a validated model or existing real data if present. Otherwise retain the demo's explicit illustrative model:
- Centre cooling: 7.5 * outputFraction * (1 - humidityFraction) / (1 + windKmh / 30) * clamp((temperatureC - 23) / 8, 0, 1).
- Radius: zero at zero output; otherwise 20 + 0.24 * outputPercent metres.
- Distance falloff inside the radius: (1 - (distance / radius)^2)^2; zero outside.
- Candidate ranking: normalised heat 50%, pedestrian flow 35%, and time remaining until shade 15%. Document the normalisation and handle already-shaded and no-shade cases consistently.

Calculate shade from the same building geometry and sun used for rendering, including courtyards, building height and the Opera House shells. Use suitable spatial acceleration. If reproducing the supplied model, sample several nearby points; shade arrival is the first time at least 60% is shaded and the condition persists ten minutes later. Natural temperature change compares the no-fog scenario now and one hour later, with time bounds handled consistently.

OpenFreeMap supplies map geometry, not live temperatures, humidity or pedestrian counts. Keep measured inputs, estimated values and sample scenarios visibly distinguishable. Describe recommendation scores as an illustrative comparison of candidates, not a proven city-wide optimum. Put concise assumptions in an English information dialog; keep implementation jargon out of the main user flow.
